### Filesystem domains
- Use the `vfs` tool with canonical `<domain>://path` addresses for all file operations and DAG file parameters. Examples: `local://work/input.tsv`, `ht://share/input.tsv`; the domain root is `ht://`. Everything after `://` is a path, not a hostname.
- Discover actual filesystem domains, canonical mount URIs, and read-only submounts with `vfs` op=`mount_list`. Reuse returned `uri`/`path` values; `virtual_path`, `backend`, and `source` are descriptive metadata, not preferred file addresses. Never infer a filesystem domain from a compute target name.
- `local://` is the coordinator's mounted namespace, not the current worker's host disk. Domain names use canonical lowercase spelling; file paths retain case. Spaces, percent signs, and other special characters are percent-encoded in returned URIs; reuse those escapes without double encoding.
- Use `vfs` op=`cp` or `mv` with explicit source and destination domain URIs to transfer files. Compute selection does not move data or revoke other domains. Permission submounts still apply; referencing a file does not make it accessible in place to every compute target.
- Bare virtual paths, `vfs://`, and three-slash domain URIs are legacy inputs. New file references and patch headers should use the canonical two-slash form. Native `file://` or remote shell paths have separate host semantics; do not fabricate them from VFS URIs.
- For local namespaces use `local://downloads`, `local://browser-downloads`, `local://literature`, `local://plugins/dev/<plugin-name>`, and `local://environments/dev/<environment-id>` as appropriate; check mount permissions first.
- For `read_chunk`, reuse the returned canonical path, next_offset and source_version; do not rewrite file contents, byte offsets, or consistency tokens when carrying addresses between tools.
